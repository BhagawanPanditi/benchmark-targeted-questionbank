# Prerequisite Question Bank — Generation Pipeline

A resumable, 9-stage LLM pipeline that turns raw benchmark problems
(`coding.json` / `reasoning.json`) into targeted diagnostic question banks:
`coding_prerequisite_questions.json` and `reasoning_prerequisite_questions.json`.
For every source problem it identifies the specific failure modes a solver
could hit and generates one easier, standalone question per failure mode — a
prerequisite question that diagnoses exactly the weakness that would cause the
source problem to be failed.

This file is regenerated by Stage 9 on every pipeline run.

## How to Run

Place your input files `coding.json` and `reasoning.json` in the project root
(record format below), then:

```bash
pip install -r requirements.txt
python run_pipeline.py
```

Optional flags:

```text
  --stages 1,2,3      # run only specific stages (comma-separated)
  --domain coding     # run for one domain only
  --resume            # default: always on; completed records are always skipped
```

The pipeline expects a vLLM-compatible OpenAI API endpoint. The base URL, API
key, and model path are hardcoded in `config.py`
(`http://localhost:30000/v1`, key `vllm`, gpt-oss-120b snapshot).

Resumability: every stage checkpoints after each record (atomic write,
`.tmp` + rename). A crashed or interrupted run is re-run with the same
command; completed records are detected and skipped, in-flight records are
finished, and nothing is re-processed. Stage 3 (taxonomy) and Stage 5
(concept graph) are one-time stages per domain: once their outputs exist,
they apply/re-derive from the existing file with zero LLM calls.

## Input Files

Each input file is a JSON **array of records** with these fields:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `benchmark` | string | yes | Benchmark name, e.g. `"HumanEval"`, `"AIME"`, `"GPQA"` |
| `sub_benchmark` | string or null | no | Subset/partition of the benchmark, e.g. `"2024-I"`; use `null` when there is none |
| `problem_id` | string | yes | Unique problem identifier — convention: `"<benchmark>/<id>"`. This is the **resume key**: on re-runs, problems whose `problem_id` already exists in a stage's output file are skipped |
| `question` | string | yes | The full problem statement |
| `answer` | string | yes | The gold answer — for coding problems a single-line expression or one-liner, for reasoning problems the exact answer. Stage 1 grounds its reasoning trace to this value: the trace must end with the single line "Therefore, the answer is: <answer>" and is verified against the gold, so the answer must fit on one line |

Example `coding.json`:

```json
[
  {
    "benchmark": "HumanEval",
    "sub_benchmark": null,
    "problem_id": "HumanEval/0",
    "question": "def has_close_elements(solution: list[float], threshold: float) -> bool:\n    # Write a function that returns true if the given list has two elements\n    # that are closer to each other than threshold.",
    "answer": "any(abs(a - b) < threshold for i, a in enumerate(solution) for b in solution[i + 1:])"
  }
]
```

Example `reasoning.json`:

```json
[
  {
    "benchmark": "AIME",
    "sub_benchmark": "2024-I",
    "problem_id": "AIME/2024-I-1",
    "question": "Let X be the number of ordered triples (a, b, c) of positive integers such that ...",
    "answer": "208"
  }
]
```

## Project Layout

```
run_pipeline.py    entry point: CLI flags, logging, stage orchestration
config.py          all settings: endpoint, concurrency/retry, thresholds, file paths
prompts/           ALL LLM prompt templates, one module per stage (no prompt
                   text lives inside the stage code)
stages/            stage logic: stage1_reasoning … stage9_readme
utils/             llm client (async, semaphore, retries, JSON parsing),
                   io (atomic save-after-every-record), similarity (Jaccard),
                   constants (severity ranks)
```

## Pipeline Stages

| Stage | Description | Input | Output |
| --- | --- | --- | --- |
| 1 | Gold-grounded reasoning generation (with answer verification) | `coding.json` / `reasoning.json` | `coding_with_reasoning.json` / `reasoning_with_reasoning.json` |
| 2 | Freeform concept extraction | `*_with_reasoning.json` | `coding_raw_concepts.json` / `reasoning_raw_concepts.json` |
| 3 | Taxonomy normalization (one-time, controlled vocabulary) | `*_raw_concepts.json` | `coding_taxonomy.json` / `reasoning_taxonomy.json` |
| 4 | Two-pass failure-mode extraction (reasoning-anchored + anticipatory) | `*_with_reasoning.json` + `*_taxonomy.json` | `coding_with_failure_modes.json` / `reasoning_with_failure_modes.json` |
| 5 | Prerequisite concept graph (DAG, cycle breaking, depth-3 closure) | `*_taxonomy.json` | `coding_concept_graph.json` / `reasoning_concept_graph.json` |
| 6 | Per-failure-mode question generation (coverage-capped) | `*_with_failure_modes.json` + `*_concept_graph.json` | `coding_questions_raw.json` / `reasoning_questions_raw.json` |
| 7 | Validation & dedup (contamination, intra-bank, LLM review) | `*_questions_raw.json` + source inputs | `coding_questions_validated.json` / `reasoning_questions_validated.json` |
| 8 | Final assembly (passed only, depth via graph BFS) | `*_questions_validated.json` + `*_raw_concepts.json` + `*_concept_graph.json` | `coding_prerequisite_questions.json` / `reasoning_prerequisite_questions.json` |
| 9 | README generation | all stats | `README.md` |
